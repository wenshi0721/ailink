# 手机端一体化（单 APK）可行性评估

- 评估时间：2026-10-20
- 评估对象：AiLink 现有架构（Android 客户端 + 自建 OneBot 桥接端）
- 结论摘要：**架构不需要"迁移到安卓"——客户端本来就是安卓原生；真正要解决的是"把桥接端搬进手机"。QQ 可以，微信不行。**

---

## 一、先拆清楚：现在到底谁跑在哪

| 组件         | 当前形态                                                                  | 运行位置       | 能否搬进一部手机                                 |
| ---------- | --------------------------------------------------------------------- | ---------- | ---------------------------------------- |
| AiLink 客户端 | Kotlin + Compose APK                                                  | 手机         | 已在此处                                     |
| QQ 桥接      | QQ NT 9.9.33 + NapCat Shell 4.18.38，正向 WS :3001                       | Windows 电脑 | **可以**（改用 Linux QQ arm64 + Termux/proot） |
| 微信桥接       | Weixin 4.1.10.27 + `version.dll` 注入（HTTP :30001）→ Node 适配器 → WS :3002 | Windows 电脑 | **不行**（见 2.3）                            |
| AI 调用      | 直连 OpenAI 兼容接口                                                        | 手机         | 已在此处                                     |

也就是说：**你缺的不是"安卓版"，是一个能跑在手机上的桥接端进程。**

---

## 二、三条技术路径与硬约束

### 2.1 硬约束一：Android 10 起不能执行应用目录里的二进制（W^X）

> 以 Android 10（API 29）为目标平台的应用，无法对应用主目录中的文件调用 `execve()`；应用只能加载内嵌在 APK 中的二进制代码。  
> —— [Android 10 行为变更](https://developer.android.com/about/versions/10/behavior-changes-10#execute-permission)

这条直接决定了"把 Node + QQ 塞进 APK 解压后执行"的朴素做法**在 targetSdk ≥ 29 时必然失败**。Termux 之所以能跑，是因为它长期停留在 targetSdk 28，代价是无法上架 Google Play（[Termux 官方说明](https://github.com/termux/termux-packages/wiki/Termux-and-Android-10)）。

**可行的绕过方式**：把可执行文件放进 APK 的 JNI 库目录（`nativeLibraryDir`），`按 libxxx.so 命名，运行时执行该路径——这是唯一被系统认可的"二进制随 APK 分发"方式。Termux 官方也把方案定为"将 deb 重打包为 JNI 库"。`

### 2.2 QQ：可行，且有官方支持的现成路径

NapCat 官方文档已经给出 Termux 部署方式，本质是：

```
proot-distro login napcat -- bash -c 'xvfb-run -a /root/Napcat/opt/QQ/qq --no-sandbox'
```

即 **proot（用户态 chroot，不需要 root）+ Debian rootfs + Xvfb 虚拟显示 + QQ Linux arm64 客户端 + NapCat 注入**。腾讯官方提供 arm64 版 Linux QQ（`QQ_3.2.7_240403_arm64_01.deb`），这条链路在社区已被验证可用（[NapCat 官方 Shell 文档](https://napneko.github.io/guide/boot/Shell)）。

对 AiLink 的意义：**代码一行都不用改**。手机上 NapCat 监听 `127.0.0.1:3001`，App 里把地址填成 `ws://127.0.0.1:3001` 即可，和连电脑完全等价。

### 2.3 微信：手机内没有可行路径

你现在的微信接入依赖三件事，缺一不可：

1. **Windows 版微信客户端**（4.1.10.27）；
2. `version.dll` 代理注入，拿到消息回调与发送能力；
3. 自写的 Node 适配层把 HTTP 转成 OneBot。

到了 Android 上，这三件事分别对应：

| 依赖                       | Android 现状                                                        |
| ------------------------ | ----------------------------------------------------------------- |
| 官方微信客户端                  | 有，但**沙箱隔离**，第三方 App 读不到它的消息与会话                                    |
| DLL 注入                   | 无对应物；Android 上要 hook 微信必须 **root + Xposed/LSPosed 模块**，普通 App 做不到 |
| Linux/arm64 微信 + hook 生态 | 微信桌面端 hook（WeChatFerry 等）只支持 Windows，**没有 arm64 Linux 版本可用**      |

剩下的唯一"无 root"路径是 **AccessibilityService 读屏 + 模拟点击**。技术上能跑通，但：

- 微信 8.0.52 之后对无障碍节点做了混淆，需要非常规手段规避，官方随时可修；
- 延迟秒级、只能处理可见界面、微信改版即失效；
- **法律风险已经落地**：2026 年已有公司因"通过无障碍权限自动化操作抖音/微信/QQ"被市场监管部门认定构成不正当竞争并罚款（3 万元），广州互联网法院也作出过行为保全裁定，要求停止提供此类软件。

结论：**微信个人号自托管"一键 App"，在现行技术+法律条件下不成立。** 这不是工程量问题，是路径不存在。

---

### 2.4 为什么 P1（容器化单 APK）只能覆盖 QQ

P1 的本质是把「Linux 运行时 + 官方客户端 + 注入器 + 协议桥」四样东西塞进 APK。QQ 这套零件齐全，微信缺两个：

| 零件                  | QQ                                                | 微信                                                                                  |
| ------------------- | ------------------------------------------------- | ----------------------------------------------------------------------------------- |
| ① arm64 Linux 官方客户端 | 腾讯提供 `QQ_3.2.7_240403_arm64_01.deb`（官方 deb / rpm） | 微信 Linux 版面向 x86_64 桌面，无面向 arm64 的可用构建                                              |
| ② 可用的注入 / hook      | NapCat 官方支持 Linux 注入（替换 QQ NT 的 `app_launcher`）   | 社区方案（WeChatFerry / `version.dll` / wxhelper）全是 Windows PE 实现，靠特征码定位 `WeChatWin.dll` |
| ③ 转 OneBot v11      | NapCat 自带                                         | 需自行实现                                                                               |
| ④ 无物理屏幕也能跑          | `xvfb-run` 起虚拟屏即可                                 | 同样需要 GUI，但①②不成立，无从谈起                                                                |

三个关键事实：

1. **hook 与客户端二进制强绑定**。现有的 `version.dll` 是按 4.1.10.27 的特征码写的，换平台等于换一套二进制，需要从零逆向。
2. **ARM 上跑不通是社区共识**。XYBot（同时支持 Linux/Windows 的微信 hook 机器人）在 FAQ 里明确写「ARM 架构能不能运行？不行」——它用的仍是 x86 的微信客户端，只是换了宿主系统；这条路都不支持 ARM，更不用说容器化再加一层。
3. **Wine / Box64 模拟 x64 微信再注入 DLL**：DLL 注入在指令翻译层下基本不成立，性能与稳定性也达不到"长期挂机"的要求。

所以 P1 做完，覆盖范围仍只有 QQ；微信必须留在一台 **x86_64 Windows**（或等效 x86 主机）。这是"P1 只有一半价值"的技术原因，不是投入不足。

**什么时候会变**：腾讯发布 arm64 的微信 Linux 客户端且存在可注入点，或微信开放个人号机器人接口（目前只有公众号 / 客服 / 企业微信）。在此之前，"一个 APK 同时接管 QQ 与微信"不成立。

## 四、推荐路线：一条主线路 + 三条备选

### 主线路：外置桥接 + 扫码配对（手机不装任何运行时）

用户明确不需要 Termux 之后，这条成为默认方案：手机只装一个 APK，桥接端留在电脑/云主机。

```
手机 App ──wss/ws──> [电脑或云 Windows]
                      ├─ NapCat  → :3001  (QQ)
                      └─ WeChat Hook → Node → :3002 (微信)
```

落地方式：电脑上跑 `node tools/pairing/make-pairing.mjs`（或双击 `bridge\scripts\show-pairing.bat`），
生成 `release/pairing.html`，手机扫码或粘贴 `ailink://` 配对码即可接入，无需手填地址与令牌。

代价：桥接主机仍需常开。收益：微信可用、耗电为零、不受手机省电策略影响、可随时换手机。

### 备选 P0：手机单机跑 QQ（需安装 Termux —— 本次已排除）

**执行清单**

| 步骤 | 操作                                                            | 通过标准                                         |
| -- | ------------------------------------------------------------- | -------------------------------------------- |
| 1  | 手机装 Termux（F-Droid 或 GitHub 版，**不要用应用商店版**，缺 `proot-distro`）  | 能打开终端，`uname -m` 输出 `aarch64`                |
| 2  | 把 `tools/termux/termux-napcat.sh` 传到手机，`bash termux-napcat.sh`     | 脚本走完 4 步，无 `[ERR]`                           |
| 3  | `bash termux-napcat.sh --start`                               | 控制台出现二维码（或容器内 `.../napcat/cache/qrcode.png`） |
| 4  | 手机 QQ 扫一扫登录                                                   | 日志出现 `登录成功` 与 `WsServer 服务启动: 0.0.0.0:3001`  |
| 5  | AiLink 新增账号：OneBot v11，地址 `ws://127.0.0.1:3001`，令牌同 NapCat 配置 | 「测试连接」显示握手成功                                 |
| 6  | 打开接入服务总开关                                                     | 账号状态变「在线」，手机 QQ 给该号发消息能在 App 里看到并自动回复        |

**常见失败**

| 现象         | 处理                                                          |
| ---------- | ----------------------------------------------------------- |
| 安装器下载失败    | GitHub 直连受限，配置代理或用镜像重试                                      |
| QQ 启动后立刻退出 | 缺 Xvfb 或 DISPLAY 未设置，确认用的是 `xvfb-run -a` 那条命令               |
| 扫码后一直转圈    | 容器内网络不通，检查 DNS；可 `proot-distro login napcat -- ping qq.com` |
| 息屏后掉线      | Termux 通知栏开启 wakelock，并把 Termux 加入电池优化白名单                   |
| 手机重启后全没了   | Termux 进程不会自启，需要手动再执行启动命令；这也是 P1 要解决的事                      |

此时手机不依赖任何电脑，微信账号仍走电脑桥接（两者可以并存，App 里就是两个账号）。

**这一步的价值**：验证"手机能不能扛住 QQ 客户端 + NapCat"这个前提。跑一周，看耗电、看被杀后台的频率，再决定要不要投入 P1。如果 Termux 里就不稳，做成 APK 也不会更稳。

> 小技巧：手机单机场景也生成配对码即可，执行 `node tools/pairing/make-pairing.mjs --host 127.0.0.1 --only qq`，
>   
> 复制 `ailink://` 那一行到 App 的「账号 → 配对码导入」，地址和令牌会自动填好并自动测试连接。

### 已实现的降门槛能力：配对码（2026-10-20）

手动填「IP + 端口 + 令牌 + 平台 + 备注」是接入环节最大的摩擦力，现已压缩成一条可粘贴的字符串：

```
ailink://pair?platform=wechat&host=192.168.1.10&port=3002&token=xxx&name=工作微信
```

- 生成：电脑上执行 `node tools/pairing/make-pairing.mjs`，自动读取 NapCat 与微信桥接的真实端口/令牌，并挑选本机内网 IP；
- 导入：App「账号 → 配对码导入」粘贴，或直接用浏览器打开该链接（`ailink://` 深链，已在 Manifest 注册）；
- 导入后自动切换到对应平台、填好地址与令牌，并**立即发起握手测试**，省掉"填完再去点测试"两步。

已验证：深链唤起与粘贴导入两条路径均能正确带入参数，实测连接微信桥接（`ws://10.0.2.2:3002`）握手 41 ms。

### P1（2–4 周）：容器化单 APK（仅 QQ）

把 P0 的东西搬进 APK，产品形态变成"一个安装包 + 首次启动自动准备环境"：

1. **打包**：proot、busybox、tar 等可执行文件改名为 `lib*.so` 放入 `jniLibs/arm64-v8a`，运行时从 `nativeLibraryDir` 执行（绕开 W^X，targetSdk 34 合法）；
2. **rootfs**：Debian bookworm arm64 精简 rootfs + QQ Linux arm64 + NapCat 打成资源包，首启解压到 `filesDir`（内置则 APK 约 300 MB，改成首启下载可压到 15 MB + 350 MB 增量）；
3. **进程托管**：前台服务里用 `ProcessBuilder` 启动 proot，托管 Xvfb/QQ/NapCat 三个进程，异常退出按退避重启，通知栏显示容器状态；
4. **二维码投屏**：NapCat 会把登录二维码存成 `qrcode.png`，App 监听文件变化直接显示在界面里，用户扫完即完成登录；
5. **适配**：arm64 机型为主（2019 年后基本覆盖），重点处理厂商省电策略、SELinux 差异、内存占用（Linux QQ 常驻约 100–200 MB）。

验收标准：冷启动到可扫码 ≤ 60 秒；连续挂机 72 小时不掉线；异常退出 3 次内自恢复。

#### P1 进展：执行链路已验证（2026-10-20）

已落地并在模拟器（Pixel 9a / Android 16 / x86_64）实测：

| 结论                                | 说明                                                                                                             |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| ✅ APK 可以执行自带二进制                   | 用静态 busybox 实测，从 `nativeLibraryDir` 成功 execve（进程正常启动并输出自身错误）                                                   |
| ✅ 必须开 `useLegacyPackaging = true` | 否则 AGP 不把 `lib*.so` 解压到磁盘，`nativeLibraryDir` 是空的，无从执行                                                          |
| ⚠️ 文件必须叫 `lib*.so`，且要处理 argv[0]   | busybox 按 `argv[0]` 分发 applet，直连路径会报 `applet not found`。解法：私有目录建同名符号链接，或 `sh -c 'exec -a busybox ...'`         |
| ❌ musl 静态包不可用                     | Alpine 的静态 busybox 在 Android 16 上被 seccomp 终止（退出码 159 / `Bad system call`）。不能用 musl 静态产物                       |
| ✅ bionic 预编译包可直接复用                | 改用 Termux 的 proot / libtalloc / libandroid-shmem（bionic 编译），裁剪后放入 jniLibs，**已在模拟器跑起 proot v5.1.107.98**，省去交叉编译 |

**执行链路的最终形态（已跑通）**

```
APK
├── jniLibs/<abi>/libproot.so            Termux 预编译 proot（bionic，266 KB）
├── jniLibs/<abi>/libtalloc.so           proot 依赖（DT_NEEDED 已就地改名）
├── jniLibs/<abi>/libandroid-shmem.so   共享内存依赖
└── jniLibs/<abi>/libproot-loader.so    guest ELF 解释器
```

关键约束（都踩过并已解决）：

1. `useLegacyPackaging = true`，否则 `nativeLibraryDir` 为空；
2. **必须直接执行 `nativeLibraryDir` 下的真实路径**。经私有目录的符号链接启动时，链接器以链接所在目录为基准，会报 `library "libtalloc.so" not found`；
3. 同时把 `LD_LIBRARY_PATH` 指向 `nativeLibraryDir`，同目录依赖才能解析；
4. proot 不依赖 argv[0]，不需要 busybox 那套 `exec -a` 技巧（那条只适用于多合一二进制）；
5. Termux 的 `libtalloc.so.2` 需要用二进制替换把 `DT_NEEDED` 改成 `libtalloc.so`（等长替换，脚本 `tools/runtime/prepare-proot.py` 自动完成）。

模拟器实测输出：`proot 5.1.107.98 / built-in accelerators: process_vm = yes, seccomp_filter = yes`，退出码 0。

这四条是 P1 的前置知识，缺一条都会多走几天弯路。当前 App 内「设置 → 手机内置运行时（QQ）」页面即为此验证入口，同时列出 proot、rootfs、NapCat 三项就绪度。

**下一步（按依赖顺序）**

1. ~~编译 arm64 版 proot~~ → 已用 Termux 预编译包解决，`tools/runtime/prepare-proot.py` 可复现装配；
2. 准备最小 rootfs（Debian arm64 的精简包），首启解压到 `filesDir/runtime/rootfs`，用 proot 绑定挂载 `/proc`、`/dev`、`/sys`；
3. 容器内安装 QQ Linux arm64 与 NapCat，`xvfb-run` 拉起，正向 WS 监听 `127.0.0.1:3001`；
4. 前台服务托管容器进程，读 `qrcode.png` 投到界面，扫码登录；
5. 账号接入方式新增「手机内置」，与 OneBot 远程并列。

验收标准：冷启动到出二维码 ≤ 60 秒；挂机 72 小时不掉线；进程异常退出 3 次内自恢复。

### P2：微信走官方通道，而不是硬闯

如果产品必须覆盖微信，正确做法是接 **企业微信自建应用 / 微信客服 API / 公众号客服消息**，在 App 里作为第三种"接入方式"与 OneBot 并列。能力边界是"只能回复通过官方入口进来的用户"，但合规、稳定、可上架。

`MessageGateway` 抽象已经为此预留位置：新增一个 `WeComGateway` 实现，注册进 `GatewayFactory` 即可，UI 与回复引擎无需改动。

#### P1 进展之二：容器已跑通（2026-10-20 20:26）

在 Android 16 模拟器（x86_64）上完成：

1. 内置 Ubuntu 22.04 base rootfs（27 MB tar.gz），首次点击「安装最小运行时」由 Kotlin 解包器写入私有目录，2616 个文件 / 676 个目录 / 212 个符号链接 / 74 MB，耗时约 30 秒；
2. 用 proot 以 `-0`（fake root）进入容器，绑定 `/dev`、`/proc`、`/sys`，执行 `uname -a` 成功。


实测输出：

```
退出码：0
Linux localhost 6.12.38-android16-5-... x86_64 GNU/Linux
---
PRETTY_NAME="Ubuntu 22.04.5 LTS"
VERSION_ID="22.04"
uid=0(root) gid=0(root)
```

**结论：无 root、无 Termux 的普通 APK，已经能跑起完整的 Linux 发行版并拿到 uid=0 的假 root。**
  
容器层不再有未知项，剩下的都是"往容器里装东西"的工程活。

两个实现细节：

- **自带 tar.gz 解包器**：Android 没有 tar 命令，busybox 的 sh 又被 seccomp 拦，所以用 Kotlin 直接解析 ustar 头（普通文件 / 目录 / 符号链接 / 硬链接），只依赖 `GZIPInputStream`，同时做了路径穿越防护；
- **AAPT 会改写 .tar.gz 资源**（实测踩坑）：打包后资源被解压成裸 `.tar` 并丢掉 `.gz` 后缀，若按原名读取会报"找不到 rootfs"。解法：资源改用 `.rootfs` 扩展名（内容仍是 gzip），App 侧按魔数 `1f 8b` 判断是否 gzip，并依次尝试 `.rootfs / .tar.gz / .tar` 三种名字。同时注意 `.tar` 在 AAPT 默认免压缩列表里，直接用裸 tar 会让 APK 从 39 MB 涨到 76 MB。
- **APK 体积**：内置 arm64 rootfs 后 APK 从 13.5 MB 增至 39 MB（gzip 内容 + `.rootfs` 扩展名）。若后续把 QQ（约 120 MB）+ NapCat（约 40 MB）也内置，会到 200 MB 量级，届时需要改成"首启下载 + 断点续传"。

#### 真机失败根因与修复（2026-10-21）

真机日志（1449 行）定位到两处问题，性质不同：

**问题一：容器继承了 Android 的 `TMPDIR`。**

```
mktemp: failed to create file via template
'/data/user/0/com.jiuguan.ailink.debug/cache/ca-certificates.tmp.XXXXXX': No such file or directory
```

Android 把 `TMPDIR` 指向应用 cache 目录，该路径在 rootfs 内不存在，`dpkg` 配置 `ca-certificates` 时直接失败。
  
修复：proot 环境显式设置 `TMPDIR=/tmp`，并在脚本启动时做一次 `mktemp` 自愈探测。

**问题二：apt 事务在 `ca-certificates` 处中断，留下半解包状态。**

```
/var/lib/dpkg/info/ca-certificates.postinst: 17: exec: /usr/share/debconf/frontend: not found
```

`debconf/frontend` 是 perl 脚本，perl 与 `ca-certificates` 在同一事务里升级，postinst 执行时 `/usr/bin/perl` 正处于替换窗口。事务中断后，`unzip` 等包停在"已解包未配置"，文件时有时无——这解释了此前"同一环境里 unzip 有时找得到、有时找不到"的怪异现象。

**修复策略：不再用 apt 退出码判定成败。**

| 原做法               | 新做法                                                                                                          |        |                   |   |                 |
| ----------------- | ------------------------------------------------------------------------------------------------------------ | ------ | ----------------- | - | --------------- |
| \`apt-get install |                                                                                                              | fail\` | \`apt-get install |   | log WARN\`，继续判定 |
| 以退出码为唯一标准         | 以「关键能力」为准：`xvfb-run / unzip / jq / curl` 四条命令 + `libgtk-3 / libnss3 / libgbm / libasound / libxkbcommon` 五个库 |        |                   |   |                 |
| 失败即终止             | 缺失时依次 `dpkg --configure -a` → `apt-get -f install` → 定向 `--reinstall`，再复检一次                                  |        |                   |   |                 |

模拟器上手动删除 `/usr/bin/unzip` 模拟该状态，修复循环成功补齐并完成安装。

#### 息屏后消息中断：Doze 导致容器停摆（2026-10-21 15:37）

现象：亮屏时收发正常，息屏后消息中断。

根因不是网络也不是登录，而是 **Android Doze**：息屏后 CPU 休眠、Wi-Fi 降功耗，容器内的 QQ/NapCat 线程被冻结，WebSocket 心跳无人应答。前台服务只保证"进程不被杀"，**不保证 CPU 不休眠**。

修复（1.0.12）：

| 措施 | 作用 |
| --- | --- |
| `PARTIAL_WAKE_LOCK`（两个前台服务各自持有） | 息屏时保持 CPU 运行，不点亮屏幕 |
| `WifiLock`（Q9+ 用 `WIFI_MODE_FULL_LOW_LATENCY`） | 避免 Wi-Fi 进入省电模式断长连接 |
| 设置页新增「息屏保持在线（电池白名单）」 | 跳转系统"忽略电池优化"授权 |

实测（模拟器）：`dumpsys power` 可见 `ACQ ailink:qq (partial)`。

**必须同时做的一步**：国产 ROM（HyperOS / EMUI / ColorOS 等）还有独立的省电策略，需要在系统设置里把应用设为「无限制」或「允许后台活动」，否则 WakeLock 也会被系统强制释放。

代价：常驻会打破深度休眠，预计每小时 3–8% 的额外耗电。

## 五、如果做 P1，几个容易踩的坑

1. **不要把 targetSdk 降到 28 来换 exec 权限**——那等于放弃所有新系统的权限适配，且应用商店一律拒绝。
2. **rootfs 不要放 `/sdcard`**：`/sdcard` 是 `noexec` 且权限模型不同，解压后直接执行会失败，必须落到 `filesDir` 再用 proot 绑定。
3. **Xvfb 是必需品**：QQ Linux 是 Electron/Qt 图形程序，没有显示服务直接退出。用 `xvfb-run` 起一个 1024x768 的虚拟屏，不要尝试 `-platform offscreen`，Qt 下不稳定。
4. **前台服务不是保险箱**：国内厂商 ROM 会连前台服务一起冻结，需要引导用户加"忽略电池优化"白名单，否则挂一夜就掉线。
5. **首启解压要考虑中断**：350 MB 解压在低端机上要 1–2 分钟，必须支持断点续解与校验，否则用户重装率高。
6. **协议版本会漂移**：QQ 每次大版本更新，NapCat 都要跟。容器化后升级路径要设计好（替换 QQ 目录 + 重注入，而不是整包重装）。

## 六、合规与法律边界

1. **非官方协议本身就有风险**：QQ/微信用户协议禁止第三方客户端接入，账号存在被限制的可能。产品若对外分发，务必在首次启动时做明确告知并留同意记录。
2. **无障碍自动化是明确的高危区**：2026 年的行政处罚与法院裁定已经把"滥用无障碍权限操作第三方 App"定性为不正当竞争，且有明确的停止令。即便技术可行，也不建议做成商品。
3. **建议的产品定位**：把 AiLink 定位为"自建服务的客户端"（用户自己部署桥接端、自己承担账号风险），而不是"帮你自动聊天的外挂"。这个定位差异直接决定风险等级。

## 七、一句话决策

- 想**手机什么都不用装**：走主线路（外置桥接 + 扫码配对），微信也能一并覆盖。
- 想**手机独立跑 QQ**：走备选 P0（需装 Termux，本次已排除），半小时，零改代码。
- 想**做成给别人的产品**：走 P1（QQ 容器化）+ P2（微信官方通道），别做微信无障碍。
- 想**微信个人号也全包**：目前没有合规且稳定的技术路径，建议放弃这个目标或改用企业微信。
